# Connector scenario consumer contract (draft)

Scenario files are used by tools outside the recorder, so changes to their fields or replay meaning can break saved evidence. This draft proposes a consumer contract while preserving the current `pdpp.connector-scenario/1` behavior. Baseline inspected: `a8ebdb978a03ae64c33bdd84f1e46b8c6f1e4f30`. It does not add a schema, CLI behavior, or a compatibility check.

## Current format baseline

The wire version is the top-level `format` string. The implementation constant is `SCENARIO_FORMAT` in [`src/scenario/format.ts`](../src/scenario/format.ts#L26); the validator accepts that exact value and rejects other values as `unsupported_format` ([`validate.ts`](../src/scenario/validate.ts#L64-L70)). Package version is not the scenario version.

The current TypeScript shape requires top-level `capture`, `connector`, `format`, and `runs`; `normalizers` is optional ([`format.ts`](../src/scenario/format.ts#L807-L813)). A capture contains `captured_at`, `complete`, `evidence_class`, `privacy_class`, and `recorder_version`; `provider_contact` is optional ([`format.ts`](../src/scenario/format.ts#L150-L163)). The connector reference requires `id`; capture-time digest and recorder metadata are optional ([`format.ts`](../src/scenario/format.ts#L59-L87)). A run requires `expected`, `interactions`, and `start`; `clock`, `environment`, and `user_interactions` are optional ([`format.ts`](../src/scenario/format.ts#L784-L805)). Each stream expectation requires `count`, `ids`, `ops`, and `record_sha256s` ([`format.ts`](../src/scenario/format.ts#L363-L393)).

The validator requires a complete capture, a non-empty connector ID, at least one run, valid run references and shapes, and valid index-aligned `ops` values ([`validate.ts`](../src/scenario/validate.ts#L73-L98), [`validate.ts`](../src/scenario/validate.ts#L259-L305), [`validate.ts`](../src/scenario/validate.ts#L384-L393)). TypeScript optionality does not by itself describe every runtime acceptance rule.

The current validator checks known fields but does not reject unknown object properties ([`validate.ts`](../src/scenario/validate.ts#L60-L70), [`validate.ts`](../src/scenario/validate.ts#L384-L393)). `ScenarioRunEnvironment` also has an explicit index signature for driver-specific additions ([`format.ts`](../src/scenario/format.ts#L767-L781)). This describes observed behavior; the compatibility guarantee below is proposed.

## Proposed compatibility guarantee

For a fixed format string, consumers should ignore unknown object properties. Producers may add optional fields only when their absence retains the existing meaning and behavior. A producer must not make a previously optional field mandatory, change a field's meaning or encoding, or require consumers to understand a new enum value under `/1`.

Changes to required fields, field meaning or encoding, enum values, ordering/canonicalization that affects comparisons, or replay semantics require an explicit format bump. A bump changes the top-level `format` discriminator, updates `SCENARIO_FORMAT`, and includes a migration statement naming the previous version and the changed semantics. Consumers identify the version from `format`; they must not infer it from the package or recorder version. Today the validator has one exact-version check, not a multi-version dispatch table, so a `/2` capture is rejected by this build.

**Proposed, pending review:** keep `/1` consumers strict about `format`, tolerant of unknown properties, and implement only the fields and enum values they know. On a breaking change, document whether the next consumer supports both versions or only the new one. The current code does not define this migration policy.

## CLI contract proposal

The commands are `scenario-record <connector>` and `scenario-verify <connector> <scenario-path>`. Current record defaults are two runs, all resolved connector streams, a timestamped path under `runs/<connector>/`, 300 seconds of inactivity, and no HAR; options are `--runs 1|2`, `--out`, repeatable `--answer`, `--answers`, `--persist-otp`, `--streams`, `--timeout <seconds>`, and `--record-har`; `--entrypoint` is a local/test override ([`scenario-record.ts`](../bin/scenario-record.ts#L20-L29), [`scenario-record.ts`](../bin/scenario-record.ts#L56-L64), [`scenario-record.ts`](../bin/scenario-record.ts#L1080-L1118), [`scenario-record.ts`](../bin/scenario-record.ts#L919-L978)). The README documents `PDPP_<NAME>_REMOTE_CDP_URL` for attaching the browser when HAR recording ([`README.md`](../README.md#L13)). Verify options are `--entrypoint`, `--require-capture-source` (off), `--json <path>`, `--timeout <seconds>` (default `300`), `--dump-records`, and `--dump-all-records` ([`scenario-verify.ts`](../bin/scenario-verify.ts#L291-L351)). No short aliases are defined in the current parsers.

Current exits: record returns `0` for complete capture, `1` for incomplete capture or connector failure, and `2` for usage errors ([`scenario-record.ts`](../bin/scenario-record.ts#L760-L768), [`scenario-record.ts`](../bin/scenario-record.ts#L2735-L2747), [`scenario-record.ts`](../bin/scenario-record.ts#L2823-L2837)). Verify returns `0` for passing replay, `1` for fatal input or replay mismatch, and `2` for usage errors ([`scenario-verify.ts`](../bin/scenario-verify.ts#L238-L260), [`scenario-verify.ts`](../bin/scenario-verify.ts#L2033-L2057), [`scenario-verify.ts`](../bin/scenario-verify.ts#L2551-L2573)). These are proposed stable meanings; human stdout/stderr wording, order, timing, and internal paths are not machine interfaces.

For machine consumption, use `scenario-verify --json <path>`. It writes `pdpp.connector-claim/1` with the claim, limitations, coverage, run/driver counts, digests, and a scenario filename ([`scenario-verify.ts`](../bin/scenario-verify.ts#L1832-L1868); authoring guide §9.2). A write failure is reported but does not change the replay exit code ([`scenario-verify.ts`](../bin/scenario-verify.ts#L1869-L1877)). This draft proposes that schema discriminator and documented fields remain stable independently of CLI prose. Whether CLI flags/defaults need their own versioning or release policy remains open; this contract does not invent another wire format or a stable stdout mode.

## Evidence, provenance, and privacy

HTTP recording captures requests made by the connector's Node process; replay compares captured exchanges and expected records/state. It is offline and does not prove that a provider remains available or unchanged ([`format.ts`](../src/scenario/format.ts#L7-L11), [`format.ts`](../src/scenario/format.ts#L191-L226)). HAR mode captures browser HTTP traffic plus storage state. Its replay proves data mapping, not page choreography; WebSocket/EventSource traffic and downloads are outside the recorded-browser contract ([`format.ts`](../src/scenario/format.ts#L695-L726)). HAR headers and cookies receive some automatic redaction, but opaque bodies and storage state remain sensitive; scenario, HAR, and storage state are local-only unless manually scrubbed ([`scenario-record.ts`](../bin/scenario-record.ts#L98-L116)).

Existing authoring guidance says to commit the claim, never the scenario capture ([`docs/connector-authoring-guide.md`](connector-authoring-guide.md#L604-L614)). **Authorized local-fixture exception for this work:** committed scenario/HAR/storage-state files may be real recorder output from an independently authored local reference connector and its local fixture site, with no account or personal data, preserving replay semantics, and documented manual plus automated scrubbing before commit. Record the fixture source, tool/repository pins, commands, date, and digests. Do not hand-author or replace the scenario JSON/HAR with synthetic output. These fixtures do not claim provider integration. Loopback-only evidence remains `synthetic-spike`, and `recorded-browser` cannot earn the canonical `recorded_replay` claim ([`format.ts`](../src/scenario/format.ts#L115-L148), [`format.ts`](../src/scenario/format.ts#L695-L716)).

## Decisions for review

1. For an explicit format bump, must a verifier support both old and new versions during migration, or may it support only one exact discriminator at a time?
2. Should CLI flag/default/exit stability be tied to package releases, or should the CLI contract remain documented but independently versioned? No separate CLI version mechanism exists in the inspected code.
3. Should the claim JSON field list become a separately normative contract, or is its existing `pdpp.connector-claim/1` discriminator and authoring documentation sufficient?
