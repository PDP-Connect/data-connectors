# Scenario consumer contract

Saved scenarios and scripted callers can stop working if a recorder or verifier changes a field, replay rule, CLI option, or claim artifact without a version change. This document freezes the intended consumer contract against baseline `a8ebdb978a03ae64c33bdd84f1e46b8c6f1e4f30`. The scenario format and validator behavior below describe existing behavior. The CLI JSON result contract is the new machine-readable interface specified here.

## Scenario JSON: `pdpp.connector-scenario/1`

Consumers identify the wire version from top-level `format`. The controlling code constant is `SCENARIO_FORMAT` in [`format.ts`](../src/scenario/format.ts#L26), and `validateFormat` accepts that exact value ([`validate.ts`](../src/scenario/validate.ts#L64-L70)). Package and recorder versions do not select the scenario format.

The TypeScript interfaces in [`format.ts`](../src/scenario/format.ts#L59-L87) and [`format.ts`](../src/scenario/format.ts#L104-L163) are the normative producer inventory. Top level requires `capture`, `connector`, `format`, and `runs`; `normalizers` is optional ([`format.ts`](../src/scenario/format.ts#L807-L813)). `capture` requires `captured_at`, `complete`, `evidence_class`, `privacy_class`, and `recorder_version`; `provider_contact` is optional. `connector.id` is required; its capture-time digest fields and `tool_version` are optional. `captured_with` contains optional source and declaration digests.

Each run requires `expected`, `interactions`, and `start`; `clock`, `environment`, and `user_interactions` are optional ([`format.ts`](../src/scenario/format.ts#L784-L805)). `start` requires `scope` and `state`; `state_from_run` is optional. `expected` requires `final_state` and `records`; `protocol_trace` is optional ([`format.ts`](../src/scenario/format.ts#L677-L693)). Each stream expectation requires `count`, `ids`, `ops`, and `record_sha256s` ([`format.ts`](../src/scenario/format.ts#L363-L393)). Each HTTP interaction requires `request`, `response`, and `seq`; request requires `method`, `origin`, `path`, and `query`, while response requires `body` and `status` ([`format.ts`](../src/scenario/format.ts#L191-L226)). The recorded-browser network driver requires `driver: "recorded-browser"`, `har_entry_count`, `har_path`, and `storage_state_path`; `environment.network` itself is optional ([`format.ts`](../src/scenario/format.ts#L728-L781)). The interfaces define further nested fields and optionality; they are the source of truth for producer shape.

The runtime validator is narrower than full TypeScript shape validation: it checks the exact format, `capture.complete === true`, a non-empty connector ID, non-empty runs, state references, run structure, and stream operation alignment ([`validate.ts`](../src/scenario/validate.ts#L64-L98), [`validate.ts`](../src/scenario/validate.ts#L259-L305), [`validate.ts`](../src/scenario/validate.ts#L384-L393)). In particular, it does not require `capture.captured_at`; old accepted inputs may omit it. Consumers must not infer that every interface type or required property is enforced at runtime.

Unknown properties are **not generally ignorable**. `/1` permits additional informational optional members at the scenario root, distinct from `format`, `capture`, `connector`, `normalizers`, and `runs`; consumers ignore these root members, and their absence must not change acceptance, replay, or claim semantics. This rule applies only to informational root members. Trace entries are compared through `JSON.stringify`, so entry keys and property order affect equality ([`verify.ts`](../src/scenario/verify.ts#L1413-L1428)); stream membership is exact ([`verify.ts`](../src/scenario/verify.ts#L2034-L2059)); final state is hashed as a whole ([`verify.ts`](../src/scenario/verify.ts#L2090-L2098)). Unknown payload, state, stream-map, trace, request, response, and driver keys can therefore change replay meaning or fail replay. The environment index signature and historical comments describing additive driver fields are implementation history, not a blanket forward-compatibility promise ([`format.ts`](../src/scenario/format.ts#L695-L700), [`format.ts`](../src/scenario/format.ts#L767-L781)). Existing optional fields may remain absent with their documented legacy behavior.

Freeze `/1` acceptance and replay semantics for advertised inputs, including older captures and optional-field absence. A breaking field, meaning, encoding, enum, ordering/comparison rule, or replay change requires a new top-level format value, an update to `SCENARIO_FORMAT`, and a migration statement that names the prior version and states whether support continues or is dropped. Do not add a multi-version engine preemptively. Dropping prior support requires an explicit rejection test and a pinned prior verifier or documented migration route; consumers must not silently skip old fixtures. Historical comments saying a driver could be added without a bump describe pre-freeze development, not future policy.

## CLI contract

The stable CLI identity is `pdpp.connector-scenario-cli/1`. It is declared in [`bin/scenario-cli-contract.json`](../bin/scenario-cli-contract.json), beside the invoked `scenario-record.ts` or `scenario-verify.ts`. A consumer resolves the actual invoked bin path and reads this sibling file; it must not use the current working directory. Missing metadata means the CLI contract is unversioned. CLI contract changes that break documented flags, defaults, exit meanings, or machine artifacts require a new contract identifier. There is no runtime `--version` flag. The metadata must ship with the bins wherever those bins are distributed; the current private npm package file allowlist excludes `bin/`, so its tarball currently ships neither the bins nor this metadata ([`package.json`](../package.json#L4-L16)).

`scenario-record <connector>` defaults to two runs, all registered streams, a timestamped `runs/<connector>/<iso>-scenario.json` output path, a 300-second inactivity timeout, and no HAR ([`scenario-record.ts`](../bin/scenario-record.ts)). Its flags are `--help`, `--json`, `--runs 1|2`, `--out <path>`, repeatable `--answer <id-or-index>=<value>`, `--answers <json-file>`, `--persist-otp`, `--streams <name,name,...>`, `--timeout <seconds>`, `--record-har`, and `--entrypoint <path>` (a local/test override); it defines no short aliases, and `--help` lists every flag and its default. The `--timeout` value must be a positive integer. If the same answer key appears in both sources, `--answers` wins over `--answer` ([`scenario-record.ts`](../bin/scenario-record.ts)). Unknown options and invalid arguments exit `2`; successful complete capture exits `0`; incomplete capture or recording failure exits `1`. An unknown connector exits `2`; an unknown `--streams` name exits `1` ([`scenario-record.ts`](../bin/scenario-record.ts)).

`scenario-verify <connector> <scenario-path>` defaults to a 300-second inactivity timeout. Its flags are `--help`, `--entrypoint <path>`, `--require-capture-source` (off by default), `--json <claim-path>`, `--timeout <seconds>`, `--dump-records <dir>`, and `--dump-all-records` (off by default); it defines no short aliases, and `--help` lists every flag and its default. The `--timeout` value must be a positive integer. `--dump-records` takes precedence over `PDPP_SCENARIO_DUMP_DIR`. Passing replay exits `0`; invalid scenario or replay mismatch exits `1`; usage errors exit `2` ([`scenario-verify.ts`](../bin/scenario-verify.ts)). Human diagnostic wording and ordering, timing, and internal paths are not machine APIs.

In JSON mode, each invocation writes exactly one compact result object and newline to stdout; human diagnostics go to stderr. The versioned stdout schema is [`bin/scenario-cli-result.schema.json`](../bin/scenario-cli-result.schema.json), identified by its `schema` field. The [`scenario-cli-json.md`](scenario-cli-json.md) guide lists every result field, type, outcome, exit mapping, and flag default. The CLI contract marker remains `pdpp.connector-scenario-cli/1`; the result schema has its own version. `command`, `status`, `exit_code`, and `result.kind` identify the command and outcome. Record results provide `outcome`, `failure_code`, `runs`, `scenario_path`, and nullable `capture_complete`. Verify results provide `outcome`, `failure_code`, `runs`, `failure_count`, nullable `claim`, and nullable `claim_artifact_written`. Record failure codes are `invalid_arguments` and `recording_failed`; verify failure codes are `invalid_arguments`, `invalid_scenario`, `replay_mismatch`, and `verification_failed`; successful results use `null`. Error text, record values, cookies, and tokens are not included in the JSON result. `--help` exits `0`; JSON usage errors return the usual `2`; recording and verification failures return the existing `1`. Consumers must branch on these fields and the process exit code, not parse diagnostic text.

For both commands, exit `0` has `status: "success"`; exit `1` has `status: "failure"`; exit `2` has `status: "usage_error"`. Record exit `0` means a complete capture or help; exit `1` means an incomplete capture or recording failure; exit `2` means invalid arguments or an unknown connector. Verify exit `0` means replay passed or help; exit `1` means invalid scenario, replay mismatch, or verification failure; exit `2` means invalid arguments or an unknown connector. `outcome` distinguishes help and each command result; `failure_code` is `null` for success and one of the documented stable codes for failures.

The schema requires the documented envelope and command result members, and permits additional object members. Consumers must ignore unknown members. Existing member names, types, nullability, and meanings are stable within `/1`; a breaking change requires a new `pdpp.connector-scenario-cli-result` version and an updated marker. Enum values are closed within `/1`; adding or changing an outcome or failure code requires a new schema version.

`scenario-verify --json <claim-path>` retains its existing side effect: it writes `pdpp.connector-claim/1` to the requested path on a passing replay. The stdout CLI result is separate and is emitted on success and handled failure. A failed replay leaves any prior claim file untouched; a claim-file write failure warns on stderr but preserves replay exit `0` ([`scenario-verify.ts`](../bin/scenario-verify.ts)). The claim's stable subset is: `schema`; string `connector`; optional string `captured_at`; required string `verified_at`; `claim` (`recorded_replay` or `diagnostic_replay`); string-array `limitations`, `coverage`, and `drivers`; integer `runs`; `captured_with` and `verified_subject`, each with nullable-string `source_digest` and `declaration_digest`; string `scenario_path`; and `scenario_status: "candidate oracle"`. If an accepted legacy scenario omits `capture.captured_at`, the claim omits `captured_at`; consumers must not expect `null` or a fabricated timestamp. Coverage values are feature tokens, not stream names. Consumers must ignore unknown additive coverage tokens and object keys, and treat `limitations` as display text rather than stable reason codes. Incompatible claim key, type, nullability, or meaning changes require a `pdpp.connector-claim` version bump.

## Evidence and privacy

HTTP recording captures connector-process HTTP exchanges and replay checks the connector's emitted records and state offline ([`format.ts`](../src/scenario/format.ts#L7-L22), [`format.ts`](../src/scenario/format.ts#L191-L226)). HAR replay feeds recorded browser HTTP traffic to the connector's browser context and checks data mapping; it does not reproduce page choreography, WebSocket/EventSource frames, or downloads, and it cannot earn `recorded_replay` ([`format.ts`](../src/scenario/format.ts#L695-L726)). A passing replay proves behavior against the capture, not current provider behavior.

Captures are local-only and may contain sensitive response bodies, HAR headers, cookies, and browser storage state; scrub before any commit or sharing ([`scenario-record.ts`](../bin/scenario-record.ts)). An authorized fixture exception allows real recorder output from an independently authored local reference connector and local fixture site, with no account or personal data, documented source/commands/pins/digests, and manual plus automated scrubbing before commit. These are synthetic-spike/local-only fixtures, not proof of provider integration. Do not hand-author or substitute scenario/HAR JSON for recorder output. The authoring guide's existing prohibition on committing private captures remains in force ([`connector-authoring-guide.md`](connector-authoring-guide.md#L604-L614)).
